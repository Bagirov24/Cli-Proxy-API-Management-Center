# SaaS Blueprint B — UX/UI спецификация (RU)

**Статус: дизайн-контракт.** Скрины, страницы и кликабельные формы
пока НЕ реализованы в работающем Management Center. Этот документ —
обязательный ориентир для будущих UI/UX изменений.

## 1. UX-принципы

1. **Понятно с первого взгляда:** объект → владелец → состояние →
   разрешённые связи → последнее действие → что делать дальше.
2. **Не показывать фиктивное здоровье:** различать `активен`, `не проверен`,
   `недоступен`, `отключён`, `ещё не поддерживается`, `ошибка проверки`.
3. **Ни одного опасного изменения без проверки:** предпросмотр изменений,
   объяснение влияния на действующие запросы, аудит, подтверждение.
4. **Не больше необходимого:** расширенные сетевые поля и grants скрываются
   под `Дополнительно`; по умолчанию рекомендованные безопасные значения.
5. **Полезные ошибки:** текст для человека + следующий шаг, но без имени,
   ID или параметров чужих ресурсов.
6. **Не требовать YAML от пользователя:** yaml остаётся доступен
   платформенному администратору как advanced/diagnostic view.
7. **Не смешивать платформенного администратора с клиентом SaaS:**
   Tenant Portal позже работает через отдельный tenant-scoped API.
8. **Нет скрытых сетевых побочных эффектов:** `Проверить маршрут` явно
   сообщает, что проверено (DNS/IP/доступность) и что осталось непроверенным.

## 2. Навигация, без захламления

Существующие разделы Core/OAuth/Plugins/Network settings **не переименовывать**
на текущем этапе. После подключения SaaS Control добавить один верхнеуровневый
раскрывающийся раздел `SaaS`:

```text
SaaS
  Обзор                    - клиенты, health, ошибки, расход
  Клиенты и проекты        - организации / приложения / CPA reference
  Аккаунты и подключения   - BYOK/BYOA, ownership, пулы
  Сеть и маршруты          - Egress Profiles, policy, проверка доступности
  Запросы и расходы        - trace, usage, budgets; после телеметрии
```

На Dashboard — максимум один компактный блок `Клиенты и подключения`
с ключевыми статусами и ссылкой в SaaS-раздел. Не дублировать страницы
`Управление плагинами` или `OAuth`.

## 3. Экран: Клиенты и проекты

**Список:** название, tenant ID (masked short), количество приложений,
аккаунтов и подключений, статус, активность; фильтр и поиск по своим данным.

**Карточка клиента:** `Обзор` / `Приложения` / `Доступ` / `Использование`.
В `Доступ` отображать только собственные или явно предоставленные
`AccessGrant` ресурсы, их scope, срок и кто выдал.

**Создание клиента (мастер):**
1. Имя и роль владельца.
2. Проект/приложение (сервис, бот).
3. Выбор подключения: BYOK или только подтверждённый провайдером BYOA.
4. Выбор аккаунта/пула с видимой принадлежностью.
5. Выбор исходящего профиля или `требуется подключение`.
6. Проверка: клиент / ключ-reference / модель / аккаунт / маршрут /
   ограничения / изменения.
7. Применение только после backend валидации и подтверждения.

Ключ CPA выдаётся пользователю **один раз**, никогда не повторяется.
Для повторного доступа — отдельная операция ротации.

## 4. Экран: Аккаунты и подключения

```text
Аккаунты и подключения                                      [+ Добавить]
Поиск по своим ресурсам...                 [Провайдер ▼] [Состояние ▼]
------------------------------------------------------------------------
[Логотип] Provider: Example        Аккаунт A / Tenant A    ● Работает
           API Key • Реальный режим            Model group: demo-model
           Исходящий маршрут: SOCKS5 EU-01     [Открыть карточку →]
------------------------------------------------------------------------
[Логотип] Provider: Example        Аккаунт B / Tenant B    ● Требует входа
           OAuth • Режим требует проверки     [Что сделать? →]
```

Это wireframe, а не реальные аккаунты.

В карточке:
- Провайдер, версия/возможности коннектора, разрешённый метод авторизации;
- владелец, проект и доступные пулы (без чужих данных);
- статус, последняя достоверная проверка, ошибки `401` / `403` / `429`;
- назначенный Egress Profile, IP только если реально проверен;
- модельный доступ и квота, способ её получения;
- `Переподключить`, `Отключить`, `Сменить исходящий маршрут` — RBAC + confirm.

**BYOK:** предоставить клиенту явный канал загрузки ключа в vault
без возврата plaintext в API/frontend; проверка валидности отдельно.
**BYOA:** только официальный разрешённый OAuth flow через внешний системный
браузер. Не поддерживаем антидетект, маскировку клиента или обход блокировок.

## 5. Экран: Сеть и маршруты

Для каждого профиля: безопасное имя, владелец, технология
`HTTP` / `HTTPS` / `SOCKS5(H)` / `Direct` / `VPN Connector`,
состояние, время последней проверки, исходящий IP (если проверен),
допустимые аккаунты, разрешённые клиенты.

```text
Сеть и маршруты                                             [+ Подключение]
----------------------------------------------------------------------------
SOCKS5 EU-01  | Владелец: Tenant A | Проверен 15:27
              | Прокси: proxy.vendor.net:1080  | Аккаунтов: 2
              | [Проверить] [Маршруты] [Настроить]
----------------------------------------------------------------------------
VPN Business  | Владелец: Platform | Коннектор не настроен
              | Нет рабочего маршрута         | [Подробнее]
----------------------------------------------------------------------------
Прямой выход  | Отключён для Tenant A по умолчанию
              | [Почему нельзя использовать напрямую?]
```

**Мастер прокси:**
1. Название и владелец (по умолчанию текущий tenant).
2. Тип: HTTP, HTTPS, SOCKS5, SOCKS5H; host и port отдельными полями.
3. Учетные данные прокси — отдельная защищённая форма, НЕ строка URL.
4. Проверка синтаксиса и запрет private/local/metadata endpoint.
5. Backend `Проверить соединение`: реальные разрешённые направления,
   DNS, resolved A/AAAA, IP, TLS, отсутствие прямого обхода.
6. Назначение аккаунтов и явные sharing grants.
7. Превью реального воздействия + сохранение в audit log.

**VPN:** в v1 показать состояние `Пока не подключено` и дорожную карту,
но не давать кнопку `Включить VPN`, пока нет проверенного connector runtime.
**Direct:** выключен по умолчанию, требуется явное разрешение владельца
и конкретной policy; нет переключения при отказе другого маршрута.

## 6. Визуальная карта и объяснение решения

```text
История запросов > Request trace
Источник → Gateway → CPA Key → Policy → Account Pool
                             → Selected Account → Egress → Provider
  ✓ пройдено                 ✕ заблокировано          · не выполнялось

Результат: ОТКЛОНЕНО
Этап: исходящее подключение
Причина: обязательное подключение недоступно.
Следующий шаг: проверьте соединение в «Сеть и маршруты».
Источник информации: СИМУЛЯЦИЯ (пока отсутствует live trace).
```

Только после настоящей телеметрии различать статус:
- `Симуляция` (вычисленное решение по snapshot);
- `Зафиксировано` (получен и сохранён факт события);
- `Проверено` (есть подтверждённые данные о реальном egress/аккаунте).

Анимация опциональна, краткая (150–250 мс), без бесконечных эффектов;
в режиме `prefers-reduced-motion` — мгновенные переключения. Не выдавать
симуляцию за живое наблюдение. Hover не должен быть единственным способом
получить информацию. По клику на этап — время, решение и понятный next action.
Секреты/промпты/заголовки Authorization/OAuth tokens никогда не показывать.

## 7. Стандартизованные UI-статусы

| Машинный статус | Текст RU | Действие |
| --- | --- | --- |
| `active / healthy` | Подключено · проверено | Последняя проверка, детали |
| `unknown` | Статус ещё не проверен | Проверить, не объявлять «здоров» |
| `degraded` | Работает с ограничениями | Посмотреть ошибку и задержку |
| `offline` | Подключение недоступно | Проверить адрес/доступность |
| `disabled` | Отключено администратором | Включить после проверки прав |
| `reauth-required` | Требуется повторный вход | Безопасная ссылка на OAuth |
| `blocked` | Доступ заблокирован провайдером | Информация и штатный support flow |
| `vpn-connector-unverified` | VPN-коннектор не подтверждён | Не отправлять запрос |
| `account-forbidden` | Нет доступа к этому аккаунту | Проверить права и владельца |
| `pool-forbidden` | Нет доступа к выбранной группе | Запросить разрешение |
| `egress-forbidden` | Нет доступа к исходящему маршруту | Выбрать свой профиль |
| `egress-direct-forbidden` | Прямое соединение запрещено | Настроить разрешённый прокси |
| `account-auth-unapproved` | Этот способ подключения не разрешён | Выбрать поддерживаемую авторизацию |
| `egress-invalid` | Адрес подключения не прошёл проверку | Исправить профиль и проверить повторно |
| `egress-unavailable` | Обязательный маршрут недоступен | Проверить соединение, нет direct fallback |
| `route-ambiguous` | Найден конфликт правил маршрутизации | Исправить конфликт в настройках |

Остальные reason codes из `resolveRoute.ts` при интеграции также
обязательно покрываются RU/EN переводами и тестами.

## 8. Явные состояния каждого экрана

Любая страница обязана поддерживать:
- `loading` с доступным skeleton или текстом;
- `empty` с объяснением, почему ничего нет, и одной релевантной кнопкой;
- `error` с retry и безопасным диагностическим кодом;
- `no permission` без раскрытия чужих ресурсов;
- `stale` с временем проверки и действием обновления;
- `success` только после подтверждённой серверной операции;
- `unsaved changes` при редактировании и возврате назад.

Поле обязательно помечается, ошибки выводятся рядом с ним;
не скрывать критичные ограничения в toast. Деструктивные действия
отдельно подтверждаются, показывая какие клиенты/маршруты затронуты.

## 9. Доступность и адаптивность

- Desktop ≥1280px: списки + detail panel, хлебные крошки, таблицы.
- Tablet 768px: карточки/фильтры, боковые панели по запросу.
- Mobile 320–430px: одна колонка, прокручиваемые шаги мастера, без
  горизонтального скролла основной формы/таблицы.
- WCAG AA: контраст текста не меньше 4.5:1; не определять состояние
  только цветом, добавить иконки + слова; фокус виден; управление клавиатурой;
  корректные labels, headings, aria-live для событий; экранные reader тексты.
- RU/EN обязательно; длинные сообщения не обрезать и не подменять строками
  технических кодов. Остальные локали — по доступным переводам проекта.
- Встроенная справка `Почему это заблокировано?` у каждого denial.
- Сохранять фильтры только локально без сохранения секретов.

## 10. UX Acceptance Criteria перед реализацией

1. Пользователь без YAML находит аккаунт, владельца и egress в ≤3 перехода.
2. Не может случайно расшарить аккаунт или прокси другому tenant.
3. Для неработающего обязательного прокси видно, почему запрос заблокирован,
   **без** кнопки `Попробовать напрямую`.
4. Для BYOA нельзя выбрать неподдерживаемый OAuth-режим.
5. Для каждого ресурса чётко видно, является ли статус симуляцией или фактом.
6. Нет открытых ключей, proxy userinfo, OAuth-токенов в DOM, ошибках, URL,
   уведомлениях и клиентских логах.
7. Контроль клавиатурой, ошибки, mobile layout и reduced motion протестированы.
8. При смене tenant UI сбрасывает/изолирует данные предыдущего tenant, включая
   кэш, сетевые ответы и локальный state.
9. Любые действия изменения настроек видны в audit с actor/resource/time.
10. Принятие нового UI требует проверки на staging с реальными
    network/service errors до разрешения публикации.
